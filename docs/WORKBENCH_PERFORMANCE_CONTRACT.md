## Product and evidence contract

1. **Measure before changing.** Profile the newly accepted Workbench at the exact accepted base before any product/source edit. Record a reproducible baseline with code SHA, browser/tool versions, viewport/mode, actions, sample count, raw measurements, observed variability, and a clear bottleneck hypothesis. Temporary local instrumentation belongs in ignored work files. Commit a baseline/checkpoint document before product source changes so ordering is auditable. Inspect render/update frequency, theme propagation, iframe messages, hidden preview work, conversion/serialization, listeners and high-frequency editing as evidence warrants; do not assume the cause.
2. Change only a demonstrated materially improvable hotspot. Choose the smallest bounded intervention justified by baseline data. Candidate techniques such as memoization, stable props/callbacks, narrower subscriptions, bounded batching/debounce, less redundant iframe work, or deferred hidden work are permitted only with measured need and preserved live responsiveness. No universal percentage target is invented; compare repeated before/after measurements with their natural variability and document whether the difference is meaningful.
3. Preserve accepted visual output, layout, behavior, Theme v3 and tactile semantics, history/Undo/Redo/Reset, import/export/persistence, Design Command Preview/Apply/Discard, all 13 mutation operations, 23 public registry resources, responsive and accessibility behavior. Do not remove functionality or weaken tests to produce a faster measurement. No Workbench redesign, state-management or preview architecture rewrite, new rendering framework, public API change, dependency, network behavior, or credential path without a demonstrated need and new owner authority where the boundary expands.
4. Preserve light/dark and narrow/wide user flows. Theme editing, Effects, sidebar tokens, preview tabs and gallery interactions must remain responsive; a debounce/throttle cannot make live preview stale or alter history grouping materially. Measure before/after using the same repeatable actions and build mode, and report measured tradeoffs or neutral results honestly.
5. If profiling finds no materially improvable bottleneck, make no speculative product edit. Preserve the baseline and negative/inconclusive evidence, verify unchanged accepted behavior and close the phase truthfully. Do not claim a performance improvement or fabricate a product promotion in that path.

Likely conditional edit surface: `apps/workbench/src/{App,PreviewFrame,LiveControls,lifecycle,history,controls}.tsx?`, closely related preview synchronization or derived computation modules, focused performance measurement scripts/tests, and evidence documents. These are possibilities, not permission to edit them without profiling. No dependency is justified at admission; existing React, browser Performance APIs, Playwright, Vitest and local tooling suffice.
